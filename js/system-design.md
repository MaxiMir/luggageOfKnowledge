# <a name="CDN"></a> 📌 Content Delivery Network (CDN)

**CDN (Content Delivery Network)** — это распределённая сеть точек присутствия (**PoP - Points of Presence**), каждая из которых представляет собой площадку с серверами CDN.

Эти узлы кэшируют и/или проксируют трафик ближе к конечному пользователю.

CDN работает поверх **DNS/Anycast**: пользовательский запрос резолвится в ближайший PoP, который:

* отдаёт контент из кэша,
* либо подтягивает его с origin (основного сервера).

> **Anycast** — метод маршрутизации, при котором один и тот же IP-адрес анонсируется из разных PoP, а маршрутизаторы доставляют запрос в ближайший по сетевой топологии узел.

---

### Назначение

Ускоряет доставку статического и мультимедийного контента пользователям по всему миру за счёт кэширования и проксирования на edge-узлах.

---

### Для чего нужен

* **Снижение латентности** — уменьшает RTT и TTFB, так как данные берутся с ближайшего PoP.
* **Разгрузка origin** — экономия исходящего трафика, CPU и диска на основном сервере.
* **Устойчивость** — выдерживает всплески трафика, DDoS-атаки, позволяет распределить нагрузку.
* **Оптимизация канала** — HTTP/2/3, multiplexing, TLS-терминация, сжатие (Brotli/Gzip).
* **Доп. функции**:
		* WAF (Web Application Firewall)
		* Bot protection (ограничение скриптового/парсингового трафика)
		* Rate limiting, IP reputation, гео-блокировки

> **RTT** (Round-Trip Time) — время, за которое сетевой пакет проходит от отправителя до получателя и обратно (туда-и-обратно)

---

### Виды

1. **Статический CDN**
   Для отдачи статических файлов (HTML, JS, CSS, изображения, архивы, APK и т. д.).
2. **Видеостриминг CDN**
   Оптимизирован для доставки видео (HLS, MPEG-DASH), live-stream с сегментацией и адаптивным битрейтом.
3. **Pull CDN**
		* CDN сам тянет ресурс с origin при первом запросе и кэширует.
		* Недостаток: при первом запросе будет холодный кэш → повышенная задержка.
4. **Push CDN**
		* Разработчик сам «заливает» файлы на CDN заранее.
		* Контент сразу доступен на edge-серверах.
		* Преимущество: нет «холодного кэша», быстрее для массовых релизов.
		* Недостаток: сложнее интеграция, нужно управлять актуальностью контента.

---

### Популярные решения

* **Cloudflare** - CDN + WAF + DDoS + Workers (edge-функции).
* **Google Cloud CDN**, **AWS CloudFront**, **Azure CDN** — интеграция с облаками.
* **Vercel**, **Netlify** — CDN + serverless-функции для фронтенд-разработки.

# <a name="LB"></a> 📌 Load Balancer (LB)

**Load Balancer (балансировщик нагрузки)** — это сервис или устройство, распределяющее входящий трафик между несколькими серверами (**backend-ами**) для обеспечения высокой доступности и масштабируемости.

---

### Назначение

Распределяет входящий трафик между backend-серверами для высокой доступности, масштабируемости и оптимальной производительности.

---

### Для чего нужен

* **Распределение нагрузки** — предотвращает перегрузку отдельных серверов.
* **Высокая доступность** — при падении одного backend-а запросы перенаправляются на другие.
* **Гибкость масштабирования** — легко добавлять/убирать серверы без простоя.
* **Оптимизация производительности** — поддержка `keep-alive`, TLS-терминации, `connection pooling`.
* **Безопасность** — скрывает внутреннюю инфраструктуру (IP серверов), может фильтровать трафик.

> keep-alive - одно соединение может обслуживать несколько запросов подряд.

> connection pooling - много соединений заранее подготовлены, и приложение/балансировщик распределяет запросы по ним

---

### Виды

1. **L4 Load Balancer** (Transport level)

* Работает на уровне TCP/UDP.
* Просто распределяет соединения по серверам.
* Быстрее, но без понимания HTTP-заголовков.
* **Плюсы**: очень быстрый, минимальная задержка, низкая нагрузка на CPU.
* **Минусы**: нет возможности маршрутизировать по URL, cookie, заголовкам — только по IP/порту.
* **Примеры**: IPVS, LVS, HAProxy (в L4-режиме).

2. **L7 Load Balancer** (Application level)

* Работает с HTTP/HTTPS.
* Может анализировать URL, заголовки, куки.
* Позволяет делать smart-routing (A/B-тесты, Geo, sticky-sessions).
* **Плюсы**: гибкость, «понимает» протокол, поддержка продвинутых сценариев (прим. роутинг по URL, домену, cookie, JWT-токену).
* **Минусы**: медленнее, чем L4, больше потребляет ресурсов.
* **Примеры**: Nginx, Envoy, Traefik, AWS ALB.

3. **Hardware Load Balancer**

* Специализированное «железо» для балансировки трафика.
* Используются в enterprise и телеком-инфраструктуре, когда нужен SLA на уровне «5 девяток» (99.999%) с гигантскими объёмами трафика.
* **Плюсы**: максимальная производительность, низкая задержка, высокая надёжность, поддержка от вендора, часто встроенные функции безопасности.
* **Минусы**: очень дорогой, требует отдельного оборудования, менее гибкий, зависимость от вендора.
* **Примеры**: F5 BIG-IP, Citrix ADC (NetScaler), A10 Networks.

---

### Популярные решения

* **Nginx**, **HAProxy**, **Envoy**, **Traefik** — open-source решения.
* **AWS ELB/ALB/NLB**, **GCP Load Balancer**, **Azure Load Balancer** — облачные.
* **F5**, **Citrix ADC** — hardware enterprise решения.

# <a name="Cache"></a> 📌 Cache

**Cache (кэш)** — это слой быстрой памяти (RAM, SSD или edge-узлы), где временно хранятся часто используемые данные для ускорения доступа и снижения нагрузки на базу данных или основной сервис (**origin**).

---

### Назначение

Хранит часто используемые данные в быстрой памяти (RAM, SSD), чтобы уменьшить задержки и снизить нагрузку на backend/БД.

---

### Для чего нужен

* **Скорость** — уменьшает latency (RTT, TTFB), ускоряет отклик для пользователя.
* **Разгрузка backend-а** — сокращает количество запросов к БД и API.
* **Снижение стоимости** — уменьшает использование CPU, дисков и сетевого трафика.
* **Устойчивость** — позволяет отдавать данные даже при временной недоступности основного источника.

---

### Виды

1. **In-memory Cache**

* Данные хранятся в RAM.
* Очень быстрый доступ (наносекунды–миллисекунды).
* **Плюсы**: максимальная скорость, простая интеграция.
* **Минусы**: ограничен объёмом памяти, данные теряются при перезапуске.
* **Примеры**: Redis, Memcached.

2. **Distributed Cache**

* Кэш хранится на кластере серверов и доступен для всех приложений.
* **Плюсы**: масштабируемость, отказоустойчивость, общий доступ из разных инстансов.
* **Минусы**: сложнее в управлении, сеть добавляет задержку.
* **Примеры**: Redis Cluster, Hazelcast, Aerospike.

---

### Популярные решения

* **Redis**, **Memcached** — in-memory / distributed cache.
* **Hazelcast**, **Aerospike** — распределённые in-memory data grids.


# <a name="RDBMS"></a> 📌 Relational Database (Реляционная база данных)

**Реляционная база данных (RDBMS — Relational Database Management System)** — это система управления данными, где информация хранится в виде таблиц (строки = записи, колонки = поля), а связи между таблицами описываются через ключи (**Primary Key, Foreign Key**).

---

### Назначение

Хранение структурированных данных с гарантией целостности и возможности сложных запросов на языке **SQL**.

Целостность данных обеспечивается несколькими механизмами:

- **Ссылочная целостность** — внешние ключи (`Foreign Keys`) гарантируют, что ссылка на запись в другой таблице указывает на реально существующую запись.
Пример: заказ не может ссылаться на несуществующего пользователя.

- **Уникальность** — первичные ключи (`Primary Keys`) и уникальные индексы предотвращают дублирование.
Пример: два пользователя не могут иметь один и тот же `id`.

- **Ограничения (Constraints)** — правила на уровне таблиц: `NOT NULL`, `CHECK`, `DEFAULT`.
Пример: сумма транзакции не может быть отрицательной.

- **Транзакционная целостность** (ACID) — операции выполняются либо полностью, либо не выполняются совсем, гарантируя корректность состояния базы.

---

### Для чего нужна
* **Структурированные данные** — хорошо подходит для бизнес-данных (пользователи, заказы, транзакции).
* **Целостность данных** — ACID-гарантии (Atomicity, Consistency, Isolation, Durability).
* **Мощный язык запросов** — SQL позволяет выполнять сложные выборки, агрегации, фильтрацию.
* **Поддержка транзакций** — безопасные операции «всё или ничего» (например, перевод денег).
* **Надёжность и зрелость** — десятилетия оптимизаций, встроенные механизмы репликации и бэкапов.

> **Atomicity (Атомарность)** - Операция либо выполняется целиком, либо не выполняется вовсе.
Пример: при переводе денег сначала уменьшается баланс у отправителя, потом увеличивается у получателя — нельзя выполнить только половину операции.

> **Consistency (Консистентность)** - После транзакции база всегда остаётся в корректном состоянии, соблюдая все правила и ограничения.
Пример: нельзя создать заказ с отрицательной суммой, если стоит CHECK amount > 0.

> **Isolation (Изоляция)** - Одновременные транзакции не мешают друг другу и дают такой результат, как если бы выполнялись по очереди.
Пример: два клиента одновременно покупают последний билет, но только один реально получит его.

> **Durability (Долговечность)** - После успешного подтверждения транзакции изменения не теряются, даже при сбое.
Пример: после коммита запись сохранена на диск и восстановится после перезапуска сервера.

---

### Виды

1. **Single-node RDBMS**

* Разворачивается на одном сервере.
* Подходит для малых и средних нагрузок.
* **Плюсы**: простота администрирования, минимальная задержка.
* **Минусы**: масштабирование только вертикальное (увеличение CPU/памяти).
* **Примеры**: MySQL, PostgreSQL, SQLite.

2. **Clustered / Distributed RDBMS**

* Несколько серверов объединены в кластер для масштабирования и отказоустойчивости.
* Поддерживает **репликацию**, **шардинг**, автоматический failover.
* **Плюсы**: высокая доступность, горизонтальное масштабирование.
* **Минусы**: сложность настройки, CAP-компромиссы (согласованность vs доступность).
* **Примеры**: PostgreSQL с Patroni, MySQL Group Replication, CockroachDB, YugabyteDB.

---

### Популярные решения

* **PostgreSQL** — мощная open-source СУБД, поддержка JSON, расширений (PostGIS и др.).
* **MySQL/MariaDB** — популярная СУБД для веб-приложений, простая и быстрая.
* **Oracle DB** — корпоративная БД с высокой производительностью и платной поддержкой.
* **Microsoft SQL Server** — интеграция с экосистемой Windows/.NET.
* **CockroachDB**, **YugabyteDB** — современные распределённые RDBMS, вдохновлённые PostgreSQL.


# <a name="NoSQL"></a> 📌 NoSQL Database

**NoSQL (Not Only SQL)** — это семейство систем управления базами данных, разработанных для работы с большими объёмами данных, высокой нагрузкой и разнообразными форматами хранения.
В отличие от реляционных СУБД с фиксированными таблицами и связями, NoSQL предлагает разные модели:

* **Key-Value** — хранение по ключу (как словарь).
* **Document** — объекты в формате JSON/BSON.
* **Column-Oriented** — данные по колонкам, оптимизированные для аналитики.
* **Graph** — вершины и рёбра для представления связей.

---

### Назначение

NoSQL применяется там, где важны:

* **Гибкость схемы** — данные можно хранить без заранее определённой структуры.
* **Горизонтальное масштабирование** — кластеры с десятков и сотен серверов, встроенное шардирование и репликация.
* **Высокая производительность** — оптимизация под массовую запись и чтение в реальном времени.
* **Eventual Consistency** — допускается временная рассинхронизация ради доступности и скорости.
* **Полнотекстовый поиск и аналитика** — встроенные механизмы поиска по документам и неструктурированным данным.
* **Разнообразие моделей** — можно выбрать подходящий тип БД под конкретную задачу: кэш, поиск, хранение графов, документоориентированные данные.

---

### Виды

1. **Key-Value Stores**

* Простая модель: уникальный ключ → значение.
* **Use-cases**:
  * Twitter — хранение сессий пользователей в Redis.
  * GitHub — кэширование API-ответов через Redis.
  * Amazon — каталог товаров в Amazon Marketplace через DynamoDB.
* **Плюсы**: сверхбыстрая работа, минимальные задержки.
* **Минусы**: нет сложных запросов.
* **Примеры**: Redis, Amazon DynamoDB, Riak.

2. **Document Stores**

* Хранение JSON-подобных документов с гибкой структурой.
* **Use-cases**:
  * Uber — хранение профилей водителей и поездок в MongoDB.
  * eBay — рекомендации товаров на Couchbase.
  * Forbes — сайт работает на MongoDB для управления контентом.
* **Плюсы**: естественно маппятся на объекты в коде, поддержка индексов и поиска.
* **Минусы**: слабее для сложных связей между данными.
* **Примеры**: MongoDB, CouchDB, Couchbase.

3. **Column-Oriented Stores**

* Данные разбиты по колонкам, а не по строкам.
* **Use-cases**:
  * Netflix — хранение истории просмотров в Cassandra.
  * Instagram — лента и сообщения в Cassandra.
  * Apple iCloud — Cassandra для синхронизации данных.
* **Плюсы**: быстрые агрегации и аналитика на больших объёмах.
* **Минусы**: хуже подходят для транзакционных операций (OLTP).
* **Примеры**: Apache Cassandra, HBase, ScyllaDB.

4. **Graph Databases**

* Данные представлены как **вершины** и **рёбра**.
* **Use-cases**:
  * LinkedIn — связи между пользователями в Neo4j.
  * eBay — анализ связей между товарами и покупателями.
  * NASA — графовая модель данных для космических миссий.
* **Плюсы**: идеальны для социальных графов, рекомендаций, сетевого анализа.
* **Минусы**: узкая специализация.
* **Примеры**: Neo4j, ArangoDB, Amazon Neptune.

---

### Популярные решения

* **MongoDB** — документо-ориентированная, с поддержкой индексов и полнотекстового поиска.
* **Redis** — key-value store с расширенными структурами данных (очереди, множества, pub/sub).
* **Cassandra** — колоночная БД для гигантских объёмов и высокой доступности.
* **Neo4j** — графовая БД для работы со связями.
* **Amazon DynamoDB** — облачная key-value/document БД от AWS.


# <a name="Search"></a> 📌 Search Engine (Поисковая система)

**Search Engine** — это специализированная система для быстрого поиска и анализа данных по тексту и структурам.
В отличие от классических БД, они используют **обратные индексы (inverted index)** и механизмы лингвистической обработки, чтобы находить документы не по точному совпадению, а по релевантности.

---

### Назначение

Позволяет выполнять полнотекстовый поиск, ранжирование и аналитику по большим массивам данных (миллионы и миллиарды документов) с миллисекундной задержкой.

---

### Для чего нужен

* **Full-text search** — поиск по ключевым словам, фразам, синонимам, формам слов.
* **Ранжирование** — результаты выдаются по релевантности (scoring).
* **Аналитика** — агрегации, статистика, фильтрация по полям.
* **Высокая производительность** — запросы обрабатываются быстрее, чем в SQL `LIKE`.
* **Масштабируемость** — горизонтальное шардирование и репликация.
* **Логирование и мониторинг** — поиск и анализ логов (ELK-стек).
* **Интеграция с приложениями** — автодополнение, подсветка совпадений, рекомендации.

---

### Виды

1. **Search Engines для документов**
* Индексация JSON/текстов.
* **Use-cases**: поиск по сайтам, интернет-магазинам, документам.
* **Примеры**: Elasticsearch, OpenSearch, Apache Solr.

2. **Search Engines для логов и метрик**

* Специализация под time-series + текстовые логи.
* **Use-cases**: DevOps-мониторинг, SIEM-системы.
* **Примеры**: Elasticsearch (ELK), Graylog.

---

### Популярные решения

* **Elasticsearch** — самый популярный движок, основа ELK-стека.
* **OpenSearch** — форк Elasticsearch от AWS, полностью open-source.
* **Apache Solr** — старейший Java-базированный поисковый движок.
* **Meilisearch** — лёгкий, быстрый и простой поисковик для приложений.


# <a name="MQ"></a> 📌 Message Queue (Очередь сообщений)

**Message Queue (MQ)** — это инфраструктурный компонент, обеспечивающий асинхронный обмен сообщениями между сервисами через очередь.
Приложение-отправитель (**producer**) кладёт сообщение в очередь, а приложение-получатель (**consumer**) обрабатывает его позже, независимо от момента отправки.

---

### Назначение

Позволяет сервисам обмениваться данными асинхронно, не блокируя друг друга, и выстраивать **надёжные, масштабируемые и отказоустойчивые** системы.

---

### Для чего нужен

* **Разгрузка сервисов** — producer не ждёт обработки, просто кладёт сообщение.
* **Гибкость и масштабируемость** — несколько consumer-ов могут параллельно обрабатывать очередь.
* **Надёжность** — сообщения не теряются при сбоях (persistent queue, ack/nack).
* **Декуплинг** — отправитель и получатель не обязаны знать детали друг друга.
* **Асинхронная обработка** — долгие задачи (отправка email, обработка видео, ML-инференс) выполняются в фоне.
* **Гарантии доставки**:
  * At most once (может потеряться).
  * At least once (гарантированно доставится, но возможно дублирование).
  * Exactly once (дорого, сложнее реализуется).

---

### Виды

1. **Traditional Message Queue (Brokered MQ)**
* Сообщения идут через брокер.
* **Плюсы**: удобная маршрутизация, подтверждения доставки.
* **Минусы**: может быть bottleneck, требует администрирования.
* **Примеры**: RabbitMQ, ActiveMQ.

2. **Distributed Log / Stream**
* Сообщения пишутся в лог (append-only), консьюмеры читают со своей позиции.
* **Плюсы**: высокая пропускная способность, горизонтальное масштабирование.
* **Минусы**: сложнее для транзакций и сложной маршрутизации.
* **Примеры**: Apache Kafka, Redpanda, Pulsar.

3. **Managed Cloud Queues**
* Облачные сервисы с auto-scale и SLA.
* **Плюсы**: не нужно управлять инфраструктурой.
* **Минусы**: привязка к вендору.
* **Примеры**: AWS SQS/SNS, Google Pub/Sub, Azure Service Bus.

---

### Популярные решения

* **RabbitMQ** — брокер сообщений, прост в настройке, богатая маршрутизация.
* **Apache Kafka** — распределённый лог, подходит для high-throughput стриминга.
* **Amazon SQS** — облачная очередь, auto-scale и высокая надёжность.
* **Google Pub/Sub** — аналог в GCP.
* **NATS** — лёгкий и быстрый брокер для микросервисов.


# <a name="ObjectStorage"></a> 📌 Object Storage (Объектное хранилище)

**Object Storage** — это хранилище «объектов» (файлов) с метаданными, доступное по HTTP(S). Объекты помещаются в **бакеты** и адресуются по ключу (path/key). 

Типичные свойства: почти бесконечная ёмкость, высокая надёжность (много копий), дешёвая стоимость за ГБ, доступ через API (S3-совместимость).

---

### Назначение

Долговременное, дешёвое, практически бесконечно масштабируемое хранение файлов: медиа, бэкапы, логи, датасеты, артефакты CI/CD.

---

### Для чего нужен

* **Масштаб и цена** — хранит терабайты/петабайты значительно дешевле дисков БД.
* **Надёжность** — высокий **durability (долговечность данных)** (11 «девяток» у облачных провайдеров).
* **Простой доступ** — HTTP/S + SDK, S3-совместимые API.
* **Гибкая политика хранения** — классы (Standard/Infrequent Access (IA)/Archive), жизненный цикл, Versioning.
* **Интеграции** — CDN, события на загрузку/удаление, аналитика (Data Lake).


> * **Standard**
  *Основной класс*: высокая доступность и низкая задержка. Подходит для «горячих» данных (часто читаемых/обновляемых).
  Дороже других, но быстрый доступ.

> * **Infrequent Access (IA)**
  Дешевле хранение, но дороже запросы. Данные доступны сразу, но SLA по доступности ниже.
  Используют для «холодных» данных, которые читают редко, но нужно быстро при запросе (например, отчёты за прошлый год).

> * **Archive (Glacier/Coldline)**
  Очень дешёвое хранение, но доступ к данным может занимать минуты–часы (надо «разморозить»).
  Подходит для архивов, бэкапов, комплаенс-данных.


> Versioning Lifecycle Policies (Жизненный цикл) - правила автоматического перемещения/удаления объектов между классами хранения: 
> Пример:
> * 0–30 дней → Standard (активное использование).
> * Через 30 дней → Infrequent Access.
> * Через 180 дней → Archive.
> * Через 365 дней → удалить.
> Это снижает стоимость: данные сами «стареют» и уходят в более дешёвые классы.

> Versioning (Версионирование) - Позволяет хранить **несколько версий** одного и того же объекта.

---

### Виды

1. **Публичные облака**

* AWS S3, GCP Cloud Storage, Azure Blob, Wasabi, Backblaze B2.
* **Плюсы**: готовый SLA, глобальные регионы, инструменты/SDK.
* **Минусы**: egress-стоимость, привязка к вендору.

2. **Он-прем / S3-совместимые**

* MinIO, Ceph RGW.
* **Плюсы**: контроль над данными/сетью, нет egress.
* **Минусы**: нужна поддержка/операционка.

---

### Популярные решения

* **Облака**: AWS S3, Google Cloud Storage, Azure Blob Storage, Wasabi, Backblaze B2.
* **on-prem (развёртывание на своих серверах, а не в облаке)**: **MinIO**, **Ceph RGW** (оба S3-совместимы).

# Шардирование 

**Шардирование** - это разделение одной большой базы на несколько независимых частей (шардов) по какому-либо критерию (обычно по ключу).

Каждый шард хранит только часть данных, что позволяет масштабировать систему горизонтально.

| Подход                  | Принцип работы                                                                                             | Плюсы                                                                                                                                    | Минусы                                                                                       | Где применяют                                                               |
| ----------------------- | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **Range Sharding**      | Деление по диапазонам ключа (ID 1–1M → шард A, 1M+1–2M → шард B)                                           | Простая логика, удобно для запросов по диапазонам                                                                                        | Hot-spot на «популярных» диапазонах, ребалансировка сложна                                   | Аналитика, данные с предсказуемыми диапазонами                              |
| **Modulo Sharding (%)** | `shard_id = key % N`                                                                                       | Простота, равномерная нагрузка при случайных ID                                                                                          | При изменении N нужно переложить почти все данные, неудобно искать по диапазону           | Небольшие кластеры с фиксированным числом серверов                          |
| **Consistent Hashing**  | Ключ хэшируется и кладётся на "кольцо" шардов; при добавлении/удалении сервера переставляется часть данных | Гибкость при масштабировании, балансировка нагрузки, минимальные данные на миграцию                                                      | Сложнее реализация, требуется виртуализация узлов для равномерности                          | Большие распределённые БД (Cassandra, DynamoDB, Riak)                       |
| **Geo-sharding**        | Данные разделяются по географическому признаку (регион/страна → отдельный шард)                            | Минимизирует задержку (данные ближе к пользователю), снижает стоимость межрегионального трафика, легче соблюдать локальные законы (GDPR) | Нужна глобальная маршрутизация запросов, сложно выполнять кросс-региональные JOIN/транзакции | Facebook, YouTube, глобальные SaaS (данные EU, US, Asia в разных кластерах) |


# Репликация

**Репликация** — это процесс копирования данных из одной базы данных (Primary/Master) на одну или несколько копий (Replica/Standby).
Она обеспечивает отказоустойчивость, балансировку нагрузки на чтение и ускоряет доступ к данным.

Отличный вопрос 👍
Да, **Master-Slave** (или Primary-Replica) — это только **один** из вариантов. На практике у репликации есть несколько архитектур:


### **Master–Slave (Primary–Replica)**

* Один **Master (Primary)** принимает все **записи (INSERT/UPDATE/DELETE)**.
* Несколько **Slave (Replica/Standby)** обслуживают **чтение (SELECT)**.
* Реплики получают копию WAL (write-ahead log) или binlog.

**Применение**: классическая схема в MySQL/PostgreSQL.
**Минус**: если мастер упал — нужна процедура failover.

---

### **Master–Master (Multi-Primary)**

* Несколько узлов могут одновременно **и читать, и писать**.
* Данные реплицируются во все стороны.
* **Применение**: MySQL Group Replication, Galera Cluster, PostgreSQL BDR.
* **Плюс**: высокая доступность, отказоустойчивость.
* **Минус**: риск конфликтов при одновременной записи (решается через **last write wins** или конфликт-резолверы).

---

### **Cascading Replication**

* Реплики могут "размножать" данные дальше.
* Схема: Master → Replica A → Replica B.
* Удобно, если есть десятки реплик (уменьшается нагрузка на мастер).
* **Пример**: PostgreSQL поддерживает "cascading replication".

---

### **Logical Replication**

* Реплицируются не байты WAL, а **логические изменения** (INSERT row X, UPDATE field Y).
* Позволяет **частичную репликацию** (только часть таблиц/колонок).
* Можно реплицировать **между разными версиями БД** или даже разными движками.
* **Пример**: PostgreSQL Logical Replication, Debezium (CDC).
Используется для миграций, интеграций с Kafka, ETL.

---

### **Synchronous vs Asynchronous**

* **Асинхронная** (по умолчанию в MySQL): мастер подтверждает запись сразу, реплики подтягивают позже. Риск потери данных при сбое мастера.
* **Синхронная**: запись подтверждается только после того, как реплика(и) сохранили изменения. Более надёжно, но медленнее.
* **Semi-sync**: мастер ждёт подтверждения хотя бы от одной реплики. Баланс между скоростью и надёжностью.

---

### **Multi-Region Replication**

* Данные реплицируются между **разными датацентрами/регионами**.
* Используется для Geo-distribution (например, пользователи из Европы читают данные из EU-реплики).
* **Пример**: AWS Aurora Global Database, CockroachDB.
