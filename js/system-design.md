# <a name="CDN"></a> Content Delivery Network (CDN)

**CDN (Content Delivery Network)** — это распределённая сеть серверов (узлов, **PoP** — Points of Presence), которые кэшируют и/или проксируют трафик ближе к конечному пользователю.
Работает поверх **DNS/Anycast**: пользовательский запрос резолвится в ближайший CDN-узел, который:
- отдаёт контент из кеша,
- либо подтягивает его с origin (основного сервера).

---

### Для чего нужен

* **Снижение латентности** — уменьшает RTT и TTFB, так как данные берутся с ближайшего PoP.
* **Разгрузка origin** — экономия исходящего трафика, CPU и диска на основном сервере.
* **Устойчивость** — выдерживает всплески трафика, DDoS-атаки, позволяет распределить нагрузку.
* **Оптимизация канала** — HTTP/2/3, multiplexing, TLS-терминация, сжатие (Brotli/Gzip).
* **Доп. функции**:
  * WAF (Web Application Firewall)
  * Bot protection (ограничение скриптового/парсингового трафика)
  * Rate limiting, IP reputation, гео-блокировки

---

### Виды

1. **Статический CDN**
   Для отдачи статических файлов (HTML, JS, CSS, изображения, архивы, APK и т. д.).
2. **Видеостриминг CDN**
   Оптимизирован для доставки видео (HLS, MPEG-DASH), live-stream с сегментацией и адаптивным битрейтом.
3. **Pull CDN**
   * CDN сам тянет ресурс с origin при первом запросе и кэширует.
   * Недостаток: при первом запросе будет холодный кеш → повышенная задержка.
4. **Push CDN**
   * Разработчик сам «заливает» файлы на CDN заранее.
   * Контент сразу доступен на edge-серверах.
   * Преимущество: нет «холодного кеша», быстрее для массовых релизов.
   * Недостаток: сложнее интеграция, нужно управлять актуальностью контента.

---

### Популярные решения

* **Cloudflare** - CDN + WAF + DDoS + Workers (edge-функции).
* **Google Cloud CDN**, **AWS CloudFront**, **Azure CDN** — интеграция с облаками.
* **Vercel**, **Netlify** — CDN + serverless-функции для фронтенд-разработки.

# <a name="LB"></a> Load Balancer (LB)

**Load Balancer (балансировщик нагрузки)** — это сервис или устройство, распределяющее входящий трафик между несколькими серверами (**backend-ами**) для обеспечения высокой доступности и масштабируемости.

---

### Для чего нужен

* **Распределение нагрузки** — предотвращает перегрузку отдельных серверов.
* **Высокая доступность** — при падении одного backend-а запросы перенаправляются на другие.
* **Гибкость масштабирования** — легко добавлять/убирать серверы без простоя.
* **Оптимизация производительности** — поддержка keep-alive, TLS-терминации, connection pooling.
* **Безопасность** — скрывает внутреннюю инфраструктуру (IP серверов), может фильтровать трафик.

> keep-alive - одно соединение может обслуживать несколько запросов подряд.

> connection pooling - много соединений заранее подготовлены, и приложение/балансировщик распределяет запросы по ним

---

### Виды

1. **L4 Load Balancer (Transport level)**

* Работает на уровне TCP/UDP.
* Просто распределяет соединения по серверам.
* Быстрее, но без понимания HTTP-заголовков.
* Примеры: IPVS, LVS, HAProxy (в L4-режиме).

2. **L7 Load Balancer (Application level)**

* Работает с HTTP/HTTPS.
* Может анализировать URL, заголовки, куки.
* Позволяет делать smart-routing (A/B-тесты, Geo, sticky-sessions).
* Примеры: Nginx, Envoy, Traefik, AWS ALB.

3. **Hardware Load Balancer**

* Аппаратные устройства (F5, Citrix).
* Используются в enterprise и телеком-инфраструктуре.

---

### Популярные решения

* **Nginx**, **HAProxy**, **Envoy**, **Traefik** — open-source решения.
* **AWS ELB/ALB/NLB**, **GCP Load Balancer**, **Azure Load Balancer** — облачные.
* **F5**, **Citrix ADC** — hardware enterprise решения.

# <a name="Cache"></a> Cache

**Cache** — это механизм временного хранения часто используемых данных в быстрой памяти (RAM, SSD или edge-узлах), чтобы ускорить доступ и снизить нагрузку на базу данных или основной сервис (**origin**).

---

### Для чего нужен

* **Скорость** — уменьшает latency (RTT, TTFB), ускоряет отклик для пользователя.
* **Разгрузка backend-а** — снижает количество запросов к БД и API.
* **Снижение стоимости** — меньше нагрузка на диски, CPU, сетевой трафик.
* **Устойчивость** — часть данных доступна даже при проблемах с основным хранилищем.

---

### Виды

1. **In-memory Cache**

* Данные хранятся в оперативной памяти.
* Очень быстрый доступ (наносекунды/миллисекунды).
* Примеры: Redis, Memcached.

2. **Application-level Cache**

* Локальный кэш в приложении (in-process).
* Подходит для небольших объёмов данных, но не шарится между серверами.

3. **Distributed Cache**

* Кэш разделён между несколькими серверами/нодами.
* Обеспечивает масштабируемость и отказоустойчивость.
* Примеры: Redis Cluster, Hazelcast, Aerospike.

4**Database Cache**

* Встроенные механизмы кэширования внутри БД.
* Например, query cache, page cache в MySQL/Postgres.

---

### Популярные решения

* **Redis** — key-value store с поддержкой pub/sub, TTL, кластеризации.
* **Memcached** — простое in-memory key-value хранилище.
* **Hazelcast**, **Aerospike** — распределённые кэши для больших систем.
